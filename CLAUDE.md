# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

`purgewave-spec.md` is the full requirements and execution plan and is the **source of truth** for everything about this app. Read it before implementing anything; this file only summarizes the parts most load-bearing for day-to-day work. When this file and the spec disagree, the spec wins — update this file to match.

All eight milestones (M1–M8) are built and verified against real acceptance criteria — both `npm run test` and, for anything with UI or filesystem surface, actually driving the running app (see "Verifying UI work" below) — with one explicit exception: **the actual Windows `.exe` installer has not been produced or run**, because this container can only cross-compile it via Wine, which hits a reproducible NSIS two-pass bug here. See "Packaging" below for exactly what was and wasn't verified, and the GitHub Actions workflow that produces a real installer on an actual Windows runner instead. Read `purgewave-spec.md` §10 for what "done" meant at each milestone; this file is the running log of what actually got built, tested, and learned along the way — treat gaps called out below as real, not hedging.

PurgeWave is a Windows desktop app (Electron + React + TypeScript + Vite + Tailwind) for triaging a local music library one track at a time: swipe right to keep, left to mark for deletion, review and confirm before anything actually leaves disk.

## Build order

Build in the milestone order laid out in `purgewave-spec.md` §10 — each milestone is independently runnable and has explicit acceptance criteria; do not start the next until the current one's criteria pass:

M1 skeleton → M2 folder choice & scan → M3 queue/reconciliation/state split → M4 swipe UI (no audio) → M5 audio preview → M6 review & disposal → M7 settings & stats → M8 themes/polish/packaging.

## Commands

Scaffolded with [electron-vite](https://electron-vite.org) (main/preload/renderer triple build). Note: `vite` and `@vitejs/plugin-react` are pinned to `^7` / `^4` respectively — `electron-vite@5`'s peer range does not yet accept Vite 8, so don't blindly bump either without checking that peer range first.

- `npm run dev` — starts the Vite dev server + Electron with HMR.
- `npm run build` — production build of main, preload, and renderer to `out/`.
- `npm run preview` — runs the production build.
- `npm run typecheck` — `tsc --noEmit` over both the node side (`tsconfig.node.json`: main + preload) and the web side (`tsconfig.web.json`: renderer).
- `npm run test` — `vitest run`, the pure-logic unit tests (queue ordering, reconciliation, card building). Co-located as `*.test.ts` next to the module under test (`src/main/library/*.test.ts`), not in a separate `tests/` tree.

Styling is [Tailwind v4](https://tailwindcss.com) via `@tailwindcss/vite`, wired into `electron.vite.config.ts`'s `renderer.plugins` (not a `tailwind.config.js` — v4 is CSS-first; the only Tailwind-specific file is `src/renderer/src/styles.css`, which also defines the §9.1 theme tokens and is imported once from `main.tsx`). `renderer/index.html`'s CSP needs `img-src 'self' data:` for the card artwork (fetched as base64 `data:` URIs over IPC, not file/network requests) — don't tighten that back to bare `default-src 'self'` or every card art thumbnail silently fails to load with a CSP console error, no thrown exception.

If `node_modules/electron` installs without downloading its platform binary (`node_modules/electron/dist` missing, `dev` fails with `Error: Electron uninstall`), run `node node_modules/electron/install.js` to force the postinstall download.

The devcontainer runs `npm install` automatically via `postCreateCommand`, and forwards the Vite dev server on port 5173. A TigerVNC + noVNC desktop is already running inside the container (`DISPLAY=:1`, noVNC on port 6080) — Electron windows render there, so screenshotting via `import -window root` (ImageMagick) against that display is the way to visually verify UI work without a browser.

## Verifying UI work

Run `npm run dev` in the background (`nohup npm run dev > /tmp/pw-dev.log 2>&1 &`), then `DISPLAY=:1 import -window root some.png` and read the PNG back to see the actual rendered window — do this for real rather than trusting that code compiles or that unit tests are enough (both `library:scan` end-to-end and a real missing→restore file cycle were verified this way in M2/M3, on top of the vitest suite). `xdotool` (`search --name`, `mousemove ... click 1`, `key`, `type --delay 5 ...`) is installed and drives both in-app UI and native OS dialogs. For the folder-choose native GTK dialog specifically: `ctrl+l` opens a location bar; type the absolute path and press `Return` — this navigates into it and leaves a live autocomplete popup covering the list area (including the "Open" button underneath it), so a click at the button's normal coordinates lands on whatever popup row is there instead. Press `Tab` first to close the popup and return focus to the dialog chrome, *then* click "Open". `Escape` cancels the whole dialog rather than just dismissing the popup, so don't use it to back out of a stray suggestion — if the path entry gets into a weird state, `ctrl+a` then `Delete` then retype is the reliable reset. Always fully `pkill -9` old Electron/vite processes (by PID from `ps aux`, not just by pattern — the pattern match is unreliable across the npm-script/electron-vite/electron process chain) before starting a new `npm run dev`, or you'll screenshot a stale window and misread it as a bug.

A one-time `sudo apt-get install -y ffmpeg xdotool` is worth doing early in a fresh container: ffmpeg (with `-c copy` remuxing + `-metadata` flags) generates large tagged-audio fixtures fast for exercising the scanner/queue/reconciliation acceptance criteria in §10, and both tools are otherwise absent from the base devcontainer image.

## Architecture

**Process split.** All filesystem work — scanning, tag reading, trashing, state file I/O — lives in the main process. The renderer is pure UI and talks to main only through the IPC contract (spec §7), defined in a shared TypeScript types file. `contextIsolation: true`, `nodeIntegration: false`, preload exposes a typed API via `contextBridge`. Keep queue ordering, reconciliation diffing, and status transitions in plain TypeScript modules with no Electron or `fs` imports — they're the logic most worth unit-testing without booting a window.

**Persistence — two JSON files, no database**, under `app.getPath('userData')`:
- `library.json` — cold: paths, tags, fingerprints. Rewritten only on scan.
- `decisions.json` — hot: statuses, timestamps, review counts. Rewritten on every swipe (debounced to 2s, force-flushed on session end / delete confirm / `before-quit`).
- `settings.json` — tiny, rewritten on settings change.

The split exists purely for write cost: `decisions.json` must stay cheap to write on every swipe regardless of library size. **A swipe write must never rewrite `library.json`.** `DecisionsStore` (`src/main/state/decisionsStore.ts`) is the debounced (2s), serialized (chained-promise) writer for `decisions.json` alone — `track:decide`/`track:undo` only ever touch it, never `library.json`, which is true by construction but still has no dedicated regression test asserting it; add one if you touch this path. All three §3.3 force-flush triggers are wired: `before-quit` (via `app.exit()` after `flush()` resolves), session end (`session:complete` IPC, called from `SwipeScreen`), and deletion confirm (`review:confirmDispose`/`review:confirmPermanent` both `await decisionsStore.flush()` before returning).

`DecisionsStore` also owns the lifetime `stats` object (§6.8): `recordDecision()`/`recordUndo()` (called from `track:decide`/`track:undo`), `recordDisposal('trashed'|'moved', bytes)` (called from `dispose.ts` per successful item), and `recordSessionCompleted()`. This was *not* wired in the first disposal pass — a real end-to-end test (Recycle Bin disposal against the fixture) showed `stats` staying all-zero in `decisions.json` despite the disposal itself working correctly, which is how the gap was caught. If you add a new kind of event that should count toward lifetime stats, it needs its own explicit `record*` call site — nothing derives stats retroactively from `d`.

All writes are atomic: serialize to `<name>.json.tmp`, fsync, `fs.rename()` over the target, rotate previous version to `<name>.json.bak`. On load, fall back to `.bak` on parse failure; if both fail, preserve the corrupt file and start fresh rather than overwrite it.

**Identity is content, not path.** A track's ID is a short sequential string (`t1`, `t2`, …), never reused. Its fingerprint (`fp`) is `sha1(64KB read from the middle of the file || size || round(durationSec))`, truncated to 16 hex chars — read from the middle specifically so ID3 tag edits at the front don't change it. Recompute `fp` only when `size` changes.

**Reconciliation** (`src/main/library/reconcile.ts`) matches by fingerprint, not path, so renames/moves/whole-tree reorganizations preserve status with no heuristics — it's a pure function (no fs/Electron imports) taking the previous `LibraryFile`/`DecisionsFile` plus this scan's freshly-read entries (or `null` to signal the root itself was unreadable) and returning the merged result or an abort. `src/main/library/scan.ts` is the fs-touching orchestrator around it: checks the root is a readable directory, walks it, skips re-reading tags for any file whose `path`+`size`+`mtimeMs` match the previous record exactly (§3.8's "a couple of seconds" rescan budget), then hands everything to `reconcile()`. A first-ever scan is just `reconcile()` called with `previousLibrary: null` — there is deliberately no separate "fresh scan" code path.

Status-transition rules (missing → reappears → restored; trashed/moved → reappears → unreviewed, etc.) are implemented and unit-tested (`reconcile.test.ts`) for every scenario spec §3.5/M3 lists by name. One spec tension resolved during implementation, worth knowing if you touch this code: §3.5 says a restored `trashed`/`moved` file should return "as unreviewed" *and* "keep its `n` count", but §3.2 is explicit that absence from `decisions.d` is the **only** representation of unreviewed and §5.1 defines pass 1 as strictly "no decisions entry" — there is no schema slot that is simultaneously absent-for-queue-purposes and present-to-hold-`n`. Implemented as: the entry is deleted outright (matching the two hard, testable rules), so `n` is lost on that specific transition. If a future spec revision wants `n` preserved here, it needs a schema change (e.g. an explicit `unreviewed` status value), not just a code fix.

Duplicate fingerprints (byte-identical files at different paths) are handled across rescans too: `reconcile()` prefers matching a previous id by exact path among candidates sharing that `fp` before falling back to any unclaimed one, so two duplicates don't randomly swap identities/history between scans.

**Changing the library root never destroys records.** No automatic pruning anywhere in the app; dormant `missing` records are only ever dropped via the explicit, confirmed "Forget dormant tracks" setting (or after a full year unseen). Getting this wrong in the destructive direction is the single worst failure mode in the app (spec §3.6).

**Queue ordering** (spec §5.1) is two fixed passes computed once at session start: pass 1 = unreviewed tracks by `birthtimeMs` ascending; pass 2 = previously-kept tracks by `reviewedAt` ascending. `delete`-marked, `trashed`, and `missing` tracks are excluded.

**Performance budgets are test assertions, not aspirations** (spec §3.7, enforced in CI against a 200k-entry synthetic index): gesture release → next card interactive in <100ms; audio audible <250ms after; 60fps during drag. This drives several concrete architectural constraints:
- Optimistic UI — animate immediately on release, fire `track:decide` without awaiting it.
- IPC never sends the whole queue — `session:start` returns ordered track IDs only; `session:getCards` windows in batches of 50.
- Two `<audio>` elements ping-ponged, prefetch depth 2, both prepared ahead of need. Implemented in `useAudioEngine.ts` — see the dedicated section below.
- The `track://` custom protocol handler must support HTTP Range requests (206 + `Content-Range`) — without this, seeking into a large FLAC transfers the whole file first. This is called out as the single biggest latency risk. Verified for real (not just by inspection): `currentTime` was observed starting at exactly `duration × 0.2` and advancing in step with wall-clock time after `play()`.
- Everything a card displays must be precomputed at scan time (album context from the `folders` map, cached artwork thumbnails, cached loudness) — nothing may require a filesystem read or index scan at display time.

**Disposal** (`src/main/disposal/`) has three modes (spec §6.7), selected in settings, defaulting to Recycle Bin: `shell.trashItem`, quarantine move (same-volume `fs.rename`, cross-volume copy+verify+delete on `EXDEV`, fingerprint-based collision handling, mirrors library folder structure), or permanent delete. `fs.unlink` (`dispose.ts`) is the only call site — reachable only through the permanent-mode setting or the explicit no-Recycle-Bin prompt.

`dispose.ts` runs all three modes through one shared loop (sidecar lookup, decision update, empty-folder tracking are identical; only the removal primitive differs per mode) and stops the **whole batch** on the first Recycle-Bin failure rather than falling back to permanent delete — the untried remainder comes back as `needsPermanentPrompt` for the renderer to ask about. `sidecars.ts` (same-basename companions always; `cover`/`folder`/`front`/`album` art only when the disposed track is the last remaining audio file in its directory — computed from `library.folders` siblings *not* in this batch and not already trashed/moved/missing) and `emptyFolders.ts` (walks upward from each affected directory, removing empty-or-leftover-only folders, stopping at `musicRoot`) are both pure-ish and unit-tested against real temp directories (not mocked fs). One correctness bug caught by those tests, not by inspection: `emptyFolders.ts`'s first draft used a `visited` guard to avoid rechecking a directory twice, which silently broke the case where a parent folder (e.g. an artist) only becomes empty *after* a second sibling album in the same batch is removed — the guard blocked the second, now-valid check. Fixed by removing the guard entirely: it's safe without it, since a directory that's already gone just fails `readdir` and the walk stops there naturally.

Verified for real against the fixture (not just unit-tested): Recycle Bin disposal of 6 tracks, quarantine move of 2 tracks (mirrored structure confirmed on disk, `movedTo` recorded) followed by a full restore back to original paths, and a permanent-delete case specifically constructed to exercise both sidecar rules at once (a lone track with a same-basename `.jpg` and an album `cover.jpg`) — correctly took both sidecars and removed the resulting two empty parent folders.

**Theming** (spec §9.1) uses semantic CSS custom properties on a `data-theme` root attribute — never conditional Tailwind classes scattered through components, never a JS-computed color. The light theme is designed independently rather than inverting dark. Every surface×text pairing actually used in the app was checked with a standalone relative-luminance/contrast-ratio Node script (not eyeballed) against real WCAG AA thresholds — 4.5:1 for the small (12px) text sizes in use, 3:1 only where a pairing is genuinely large-text-or-larger. That check caught `--text-muted` failing AA at its original values in *both* themes (light `#7a7a7a` only hit ~4.3:1 against the card background; dark `#7d7b87` similarly fell short) — corrected to `#6f6f6f` (light) and `#8c8c8c` (dark), applied consistently across all three theme-token blocks (`:root`, the `prefers-color-scheme: dark` media block, and `:root[data-theme='dark']`). Artwork-derived background scrims (§9.1's other AA concern) were deliberately not built: the card layout never overlays text directly on top of artwork — text always sits on the solid card-background token, artwork fills its own region — so there's no text-over-image pairing that needs a scrim in this design. If a future layout change puts text over artwork, this reasoning no longer holds and a scrim treatment needs to be added then.

No-flash-on-launch (§9.1): `src/main/index.ts`'s `resolveBackgroundColor()` reads `settings.theme` (falling back to `nativeTheme.shouldUseDarkColors` when `theme === 'system'`) and sets `BrowserWindow`'s `backgroundColor` option before the window is ever shown, so the native window paints the correct theme's background from frame one instead of flashing white/default while the renderer boots.

**Swipe UI** (`src/renderer/src/session/`) decouples the *data model* from the *visual exit* on purpose, because §3.7 requires the next card to be interactive within 100ms while the departing card's exit animation is still playing (220–320ms): `SwipeScreen.tsx` advances `currentIndex` and fires `track:decide` **synchronously** the instant a decision commits (`SwipeCard`'s `onCommitted` callback), while the committed card itself is *also* pushed into a separate `exiting` list and keeps rendering — same component instance, same motion values — until its own `onExitAnimationComplete` fires. `queue.ts`'s output is used as a fixed array indexed by `currentIndex`, not a spliced/shifted array: undo is then just `currentIndex--`, since `queue[currentIndex]` is automatically the undone card again and the old front card is automatically second-in-line — no array surgery needed. The undo stack (capped 20, per spec) lives in React state; each entry's `previousEntry` is reconstructed from the `Card.pastReview` field captured when the card was first fetched (not re-queried from main), which works because a track id appears at most once per session.

Two real bugs worth knowing before extending this code, both found by actually running the app (not caught by typecheck/build/unit tests):
- **React 19 StrictMode double-invokes state-updater functions** (the callback form of `setState`) in dev, specifically to catch impurities — so any side effect placed inside one (an IPC call, another `setState` call) runs *twice*. `undo()` originally read the undo stack via `setUndoStack(prev => { ...side effects...; return prev.slice(0,-1) })`; every undo silently double-fired. Fixed by mirroring the stack into a ref (`undoStackRef`, kept in sync via a `useEffect`) and reading from the ref inside a plain `useCallback`, so `setUndoStack` itself only ever receives a pure new-array value. If a bug looks like "this ran an extra time only in dev," suspect a setState updater with a side effect inside it.
- **The prefetch effect must not commit state before its async work resolves.** The windowed-prefetch effect (`session:getCards` in batches of `PREFETCH_WINDOW`) originally called `setWindowEnd(nextEnd)` synchronously, then awaited the fetch. StrictMode's dev-only double-effect-invocation (mount → cleanup → mount again) meant the *first* invocation's promise resolved into a closure whose `cancelled` flag the cleanup had already flipped, while the *second* invocation saw the watermark already advanced and skipped fetching entirely — net result, no cards ever loaded, with zero errors anywhere. Fixed by moving the watermark advance inside the `.then()`, alongside the `setCards` call, so both commit together only when a fetch actually completes.

Both bugs produced *silent* failures (blank card stack, or double-counted undo) with nothing in the console — screenshotting the running app after every non-trivial renderer change is what caught them, not `npm run typecheck`/`build`/`test`.

M8 pass found three concrete deviations from spec §9.3's motion constants in `SwipeCard.tsx`, all cosmetic (nothing crashed, nothing was functionally wrong) but each measurably off from the spec-exact feel: (1) the intent-feedback opacity ramp used raw pixel thresholds (`[15,150]`/`[-150,-15]`) that didn't scale with the card's actual `max-w-md` (~448px) width — changed to width-relative approximations (`[67,155]`/`[-155,-67]`, ≈15%–35% of card width) so the feedback intensity ramp is consistent regardless of viewport; (2) exit distance was `containerRef.offsetWidth * 4`, not the spec's explicit "1.4× viewport width" — changed to `window.innerWidth * 1.4`; (3) the opacity fade-out was timed `{duration: durationSec, delay: durationSec * 0.6}`, which runs the fade for the *entire* duration starting 60% in — meaning it extends past the exit animation's own end — changed to `{duration: durationSec * 0.4, delay: durationSec * 0.6}` so the fade completes exactly as the exit does, over the spec's intended last 40% of the timeline. These were verified via `typecheck`/`test`/`build` and reasoned through against the spec's numbers, but not re-verified visually via live pointer-drag screenshotting in this pass — the underlying drag mechanics were thoroughly screenshot-tested earlier in M4; if you touch this file again, a live drag-and-release visual check is worth doing since it wasn't repeated here.

**Keyboard shortcut discoverability** (§6.4): `keymap.ts` gained a `'help'` intent bound to `?`. `SwipeScreen.tsx` renders a `<dl>`-based modal listing every binding, toggled by `?` and dismissed only by `Escape` or its own Close button — while open, `onKeyDown` short-circuits every other intent (arrow keys, space, etc. do nothing) so a stray keypress can't fire a swipe decision underneath the modal. There's also a small circular "?" button in the chrome for anyone who doesn't know the shortcut exists, which is the whole point of this feature.

**Empty states**: `SwipeScreen.tsx`'s end-of-queue screen and `ReviewScreen.tsx` both now distinguish "you swiped through everything and there's nothing left" from the generic zero-counts summary — checked via `queue.length === 0` / `keep.length === 0 && del.length === 0` respectively, showing "Nothing to review" / "Nothing marked for keeping or deletion right now" copy instead of a stats block with every number at zero.

**A scrollbar flashed in during every exit animation.** A card mid-exit translates via a raw `x` transform to ~1.4× viewport width (`playExit` in `SwipeCard.tsx`) — far past the bounds of its `position: relative` stack container, which had no `overflow` constraint, nor did `body`. Browsers include transformed content in an ancestor's scrollable overflow area unless something clips it, so the document briefly grew wide enough to scroll every single swipe. Fixed with `overflow-hidden` on the swipe-stack container (`SwipeScreen.tsx`, the primary fix — it's the direct ancestor and clips at the source) plus `overflow-x: hidden` on `body` in `styles.css` as a defense-in-depth safety net for any future transform-driven overflow elsewhere in the app.

**Audio preview** (spec §6.5, `src/main/protocol/trackProtocol.ts` + `src/renderer/src/session/useAudioEngine.ts`):
- `track://<trackId>` is routed **by track ID, not by raw path** — the renderer can only ever ask for an ID it was already handed via `session:getCards`, so there's no path-traversal surface to validate at all (unlike, say, a future quarantine-folder picker, which does need the §7 "validate every path crossing IPC" rule). The scheme is registered privileged (`stream: true`, `supportFetchAPI: true`, `corsEnabled: true`) via `protocol.registerSchemesAsPrivileged()` at **module load time**, before `app` is ready — call this too late and registration silently no-ops. `corsEnabled: true` specifically is required because the dev-mode renderer runs on the `http://localhost:5173` Vite origin, which makes every `track://` request cross-origin; without it every `<audio>` load fails with a CORS console error and no thrown exception anywhere. `renderer/index.html`'s CSP needs `media-src 'self' track:` to match.
- `useAudioEngine.ts` owns two `<audio>` elements for the life of a session, each routed through its own `GainNode` (`MediaElementAudioSourceNode → GainNode → destination`) on one shared `AudioContext` — the GainNode is what does fades and normalization; `HTMLMediaElement.volume` is left at 1 and never touched for that purpose. `activeIndexRef` tracks which element is *actually audible right now* (used only by playback controls — toggle/replay/live volume changes), updated after the real fade/play happens; a separate `assignedIndexRef` tracks which slot the *current front card* has claimed, committed synchronously the instant a swipe advances the front card, before any `await`. advancing swaps onto whichever element the *next* card was already prepared on (ping-pong), fading the outgoing one out and pausing it before the incoming one starts (see the "never overlap" fix below), and prepares the *new* standby element for whatever `nextCard` becomes once the queue advances.

  Real bug, found only by actually swiping through the packaged app (not by inspection or by the unit-test suite, which doesn't touch this file at all): **swiping past the first card played the audio of the card *two ahead*, not the one now on screen.** The front-card-activation effect and the next-card-prefetch effect are two separate `useEffect`s that both read/write which of the two `<audio>` slots is "active" — but the activation effect's assignment of that shared index used to happen *after* an `await prepare(...)`, while `prepare()` returns near-instantly (via an already-resolved promise, since the standby slot is normally already prefetched) — and `await` on an already-resolved promise still defers to a microtask, not the same synchronous tick. React runs both effects synchronously, in the same commit, *before* that microtask has a chance to run — so the next-card-prefetch effect read the *stale* index, computed the *same* slot the activation effect was mid-claiming as its own "standby", and immediately overwrote that slot's `src` to the next-next track while the activation effect's still-pending `play()` call was about to fire on it. Net effect: the visible card and the audible track were reliably one track apart on every swipe once prefetch had caught up (i.e. almost always). Fixed by splitting the single index into two: `assignedIndexRef` (which slot belongs to the current front card, committed synchronously, before any `await`, so the sibling effect always sees the current claim) and `activeIndexRef` (which slot is truly making sound, still updated only after the real fade/play completes, for playback-control correctness). Verified for real via a Chrome DevTools Protocol trace instrumented with temporary logging comparing each `play()` call's requested track ID against the audio element's actual `src` at that moment — confirmed a mismatch before the fix and an exact match across four consecutive swipes after it.
- Two-tier normalization per §6.5: a track's own `replayGainDb` (from tags, cached on `Track`/`Card`) is preferred; only when absent does `useAudioEngine` measure RMS via an `AnalyserNode` over ~400ms after playback starts and derive a clamped (±12dB) correction, applied by re-targeting the GainNode's ramp mid-fade so the adjustment lands inside the 1s fade-in and is inaudible. The measured value is then persisted via `track:gain` → `library.tracks[id].replayGainDb`, so it's measured at most once per file — confirmed for real (not just by code review): a fixture track with no ReplayGain tag had `replayGainDb` appear in `library.json` after its first play.
- Seek-fallback (§3.7 rule 4) is tracked in a module-level `slowStartTracks` `Set` (session-scoped, not persisted): if seeking to the configured start offset doesn't land, or takes longer than 400ms to prepare, that track ID is remembered and starts from 0 on every subsequent play in the same session.
- **The outgoing and incoming tracks must never play simultaneously — §6.5 says so explicitly ("stop the outgoing track before starting the incoming one. Never overlap"), but the original `activate()` violated it**: it kicked off the outgoing's 200ms fade-out and the incoming's `play()` + 1s fade-in in the same synchronous block, so for the full 200ms window both `<audio>` elements were genuinely decoding and mixing at once on every single swipe. Found while investigating a user report of audio stuttering that got worse while dragging — doubling the decode/mix workload at exactly the moment a drag is most likely starting is a plausible contributor, though not confirmed as *the* root cause (unverified — this sandbox can't profile real audio glitches). Fixed regardless, since it's a clear-cut spec violation either way: `activate()` now awaits the 200ms fade-out and pauses the outgoing element *before* starting the incoming one, so there's a brief silence-to-silence handoff (outgoing fades to 0, then incoming starts from 0 and fades up) rather than a true overlap. Still comfortably inside the §3.7 <250ms audible-after-release budget (~200ms in the common already-prefetched case). If the user reports stuttering persists after this, the next place to look is main-thread contention from `MediaElementAudioSourceNode`'s decode pipeline under drag-frame load — needs profiling on the actual machine it reproduces on, not something fixable blind from this container.
- `AudioEngineHandle` exposes `isPlaying`, driven by `play`/`pause`/`ended` listeners attached to both `<audio>` elements at creation, each filtered to only update state when the event's target is whichever slot `activeIndexRef` currently points at — this specifically avoids the outgoing element's own `pause()` call (fired 200ms into every crossfade) clobbering `isPlaying` back to `false` right after the incoming element already started. Drives an explicit play/pause button rendered in the card's artwork corner (`SwipeCard.tsx`, bottom-right, only for the true interactive front card) — added alongside the pre-existing implicit center-zone-click toggle for discoverability, per user request. The button stops pointerdown/pointerup propagation so pressing it can't also register as a card zone-click or initiate a drag.
- **Preview start position is a setting, not a hardcoded constant** — `Settings.previewStartRatio` (0–0.5, default 0.2, i.e. spec's original 20%), editable via a Settings-screen slider. `useAudioEngine`'s `AudioEngineSettings.previewStartRatio` feeds both `prepare()`'s initial seek and `replay()`'s reset-to-start offset; there's no in-session control for it (only reachable from the Settings screen, which a session can't be mid-way through), so `SwipeScreen` loads it once alongside autoplay/volume/normalize but never writes it back. Verified for real via a CDP trace: set to 45% through Settings, persisted to `settings.json`, and a fresh session's `prepare()` computed exactly `duration × 0.45` as the seek target.
- **There is no playback duration cap.** Preview playback starts at the configured offset and plays to the natural end of the file via the plain `<audio>` element — there's no listener that stops it early, no "excerpt length" setting, and no auto-advance on end. It only stops when the user swipes away (triggering the 200ms fade-out), pauses, or the track finishes on its own. If a bounded preview length is ever wanted, that's unbuilt — nothing in `useAudioEngine.ts` currently references a stop point.

**Settings** (spec §8, `SettingsScreen.tsx`) now covers the full table — autoplay/volume/normalize, side-click decisions, disposal mode + quarantine folder (with the plain-language explanation copy §8 asks for), remove-sidecars/remove-empty-folders (both now real toggles feeding `dispose.ts`'s `DisposeDeps`, not hardcoded-on), theme, check-for-updates (persisted; the actual update check is still M8's job), plus the "Forget dormant tracks" action (preview-then-confirm, `library:previewForgetDormant`/`library:forgetDormant`, built on `dormant.ts`'s `findDormantTracks()`). `SwipeScreen.tsx`'s autoplay/volume/normalize state now loads from and persists to `settings.json` (via `getSettings`/`updateSettings`) instead of the `localStorage` stand-in M4/M5 used.

Two more real bugs found only by actually restarting the app and clicking through Settings, not by inspection:
- **`writeJsonAtomic` had no protection against overlapping concurrent writes to the same path.** `SwipeScreen`'s three separate settings-sync `useEffect`s (autoplay/normalize/volume) all fire in the same tick when settings first load, each calling `updateSettings(...)` unawaited — three concurrent `settings:update` IPC calls raced on the shared `settings.json.tmp`, and the loser's `rename()` threw `ENOENT` because the winner had already moved the file out from under it. Real crash, logged in the main process console, first seen while testing M7's stats reconciliation. Fixed by giving `writeJsonAtomic` a per-path promise chain (`src/main/state/atomicWrite.ts`) so concurrent calls for the same file serialize automatically — callers don't need to coordinate. `DecisionsStore` already had its own version of this same pattern; this generalizes it to every `writeJsonAtomic` caller. Regression test: `atomicWrite.test.ts` fires five unawaited concurrent writes at one path and asserts the last one wins cleanly.
- **Loading an older `settings.json` silently zeroed out every field the schema had grown since it was written.** M6's `settings.json` only ever had `disposalMode`/`quarantineFolder`; M7 added eight more fields. `readJsonWithFallback<Settings>()` happily parses the old, now-incomplete object, and `settings = loaded ?? createDefaultSettings()` only falls back to defaults when the file is entirely *absent* — a partial object is still truthy, so every new field silently loaded as `undefined` (every checkbox in Settings rendered unchecked, `checked={undefined}` being falsy, regardless of its real default). Fixed by merging over the default object (`{ ...createDefaultSettings(), ...loaded }`) instead of replacing it. This is a schema-migration concern that will recur any time a new field is added to `Settings`, `LibraryFile`, or `DecisionsFile` — merge over defaults on load, never trust a loaded object to be complete just because it parsed.

**Stats** (spec §6.8, `src/main/library/stats.ts`, `StatsScreen.tsx`) computes everything from state already maintained elsewhere — no new tracking infrastructure, per the spec's own instruction. `totalKept`/`totalPendingDelete` are live counts over `decisions.d`; `totalDisposed`/`bytesReclaimed`/`bytesMoved`/`sessionsCompleted` come straight from `DecisionsStore`'s `stats` object (see above); the weekly bar chart buckets each track's *current* `r` (reviewedAt) timestamp into calendar weeks — since `r` is overwritten on re-review, this is a snapshot of latest-decision timing, not a true historical event log, which is an intentional reading of "no new tracking infrastructure" rather than a limitation to fix. Verified for real: a controlled 5-decision session (2 discard, 3 keep) followed by Recycle Bin disposal produced `5 reviewed · 3 kept · 60% keep rate · 144 KB reclaimed · 1 session`, matching hand-counted expectations exactly, and `993 unreviewed` on a 1005-track library reconciled exactly against `1005 - (5 decided + 7 already-missing) = 993`.

Dormant-track forgetting (§3.6) has two halves, both implemented: the **manual** one (`findDormantTracks()` in `dormant.ts`, the Settings action above) surfaces `missing` records unseen for 20+ scans, sorted longest-unseen-first, and drops them from both `library.tracks` and `decisions.d` only on explicit confirm; the **automatic** one lives inside `reconcile.ts` itself — every transition to `missing` now stamps `x: <now>` (spec's `x` field is documented as trashedAt/movedAt, reused here for missing-since; restoring a `missing` record back to `keep`/`delete` strips `x` along with `was` so a live entry never carries a stale "missing since" stamp), and on each scan, any record still `missing` after a full year (`now - x >= 365 days`) is auto-dropped — the one sanctioned exception to "no automatic pruning" (§3.6's own words), surfaced via `ScanResult.pruned` (previously always 0, unused since M2). Both halves are unit-tested with an injectable `now` in `reconcile()`'s input rather than relying on real wall-clock time.

The quarantine folder is excluded from scans via `scan.ts`'s `quarantineFolder` param feeding `walkAudioFiles`'s `excludeDirs` — verified indirectly (quarantined files didn't reappear as new library entries after a rescan) but not with a folder nested *inside* the library root specifically, which is the harder case §3.5/§6.7 call out explicitly. Test that case before relying on it.

The review screen (`ReviewScreen.tsx`, `review:getMarked`) shows two lists — "Deleting" is every track library-wide currently marked `delete` (matches the persistent, cross-session nature of pending deletions in §6.2's resume flow); "Keeping" is scoped to *this session's* kept-track ids, passed in from `SwipeScreen`'s `SessionSummary.keptIds`, not a library-wide dump of every ever-kept track (which the spec doesn't actually ask for and wouldn't be reviewable in one sitting). "Back to swiping" from the review screen is **not implemented** — ending a session is currently terminal, matching M4's original scope; review's "Back" button returns to the library screen, not to a resumed queue. Revisit if a future milestone needs the "extends a capped session" behavior from §6.6. Each row is title (bold) on top, artist (smaller, `--text-muted`) below, not a single "title — artist" line — a user-requested change from the original single-line layout, for easier scanning of a long list.

**Scanning** (spec §3.8, `src/main/library/`) walks the tree, then processes files through a 4-worker concurrency pool (`scan.ts`), reading tags (`readTrack.ts`), fingerprinting (`fingerprint.ts`), and resolving artwork (`artwork.ts`) per file, emitting progress every 250 files. Two library-specific interop gotchas, already handled, worth knowing before touching this code:
- `music-metadata` is ESM-only; the main process bundle is CJS (electron-vite's default). A static `import` of it at the top of a main-process file will throw `ERR_REQUIRE_ESM` at runtime even though `npm run build`/`typecheck` pass clean. `readTrack.ts` loads it via a dynamic `await import('music-metadata')` instead — keep that pattern for any other ESM-only package added to main/preload.
- `sharp` (used for the artwork → `art/<fp>.webp` cache) logs `[SharpElectronLinux]` warning about binary compatibility on load, but has worked correctly in real testing under Electron's Node on this container (N-API is ABI-stable, no rebuild needed) — verified by actually generating and reading back a `.webp` thumbnail from scanned artwork, not just by the build succeeding. If it ever does fail in practice, `artwork.ts` already degrades gracefully (`extractArtwork` returns `null` rather than throwing), so a track without art is not a scan failure.

## Packaging

`electron-builder.yml` targets NSIS (x64) for Windows: `appId com.purgewave.app`, installable-directory-changeable, desktop + start-menu shortcuts, output to `release/`. `npm run dist` runs `electron-vite build` then `electron-builder --win`.

**This container cannot produce the final `.exe`.** `npm run dist` gets all the way through the electron-vite build, `@electron/rebuild` (native module rebuild for `sharp`), and app packaging — `release/win-unpacked/` ends up with a valid Windows PE32+ executable, confirmed with `file` — but fails at the final NSIS-wrapping step:
```
File: "...\PurgeWave Setup 0.1.0.__uninstaller.exe" -> no files found
Error in macro installApplicationFiles
```
Reproduced twice, including after clearing electron-builder's NSIS cache. This is a known category of Wine/NSIS two-pass-build interaction issue (see electron-builder issues #3343, #4724, #4875 — related, not identically resolved) with no reliable one-line fix; **don't re-attempt Wine-side debugging of this** without new information, it already ate real time here for no result. The actual, electron-builder-recommended fix is to build on real Windows, which is what `.github/workflows/build.yml` does: runs on `windows-latest`, does `typecheck` + `test` + `npm run dist`, uploads the resulting `.exe` as a build artifact, and (on a `v*` tag push, with `GH_TOKEN` set) publishes to GitHub Releases via electron-builder's built-in `publish` config. Before that workflow can actually publish, `electron-builder.yml`'s `publish.owner`/`publish.repo` placeholders need to be swapped for a real GitHub repo.

`src/main/updater.ts` wires `electron-updater` per §11 (check on launch, silent background download, install on next quit — `autoInstallOnAppQuit` is the library default, no extra code needed for that part), gated by the `checkForUpdates` setting and `app.isPackaged` (a no-op in dev). **Not exercised end-to-end anywhere** — that needs a real packaged build pointed at a real GitHub Releases feed, neither of which exist yet in this sandbox. Treat it as implemented-but-unverified until tested against an actual release.

**`npm run dist:local`** — run this after every change the user needs to try on their own Windows machine, so they can test the latest build immediately without a commit/push/CI round-trip. It's `electron-vite build && electron-builder --win --dir`, then copies `release/win-unpacked/` to `PurgeWave-win/` at the project root (overwriting whatever was there). `--dir` deliberately skips the NSIS step — that's the exact step broken under Wine in this container (see above) — so this produces an unpacked-but-fully-functional `PurgeWave-win/PurgeWave.exe` plus its resources, not a single installer file. `PurgeWave-win/` is gitignored; it's a local scratch artifact, not something to commit. After overwriting it, a brand-new `.exe`/`.asar` pair on this 9p-mounted (`/workspaces` is a Windows-host `drvfs` mount under WSL2) path is sometimes transiently locked for a few seconds — almost certainly Windows Defender's real-time scan running against the newly-materialized executable, not a still-running process (confirmed: Task Manager showed nothing, and the lock cleared on its own on retry). If `rm -rf PurgeWave-win` fails with `Input/output error`/`Permission denied` mid-script, just retry the command a few seconds later rather than hunting for a phantom process.

Real bug caught by actually running the packaged `.exe` on Windows, not by inspection: **the very first `dist:local`/`dist` build crashed on launch with `sharp: Could not load the "sharp" module using the win32-x64 runtime`.** Root cause — `sharp` ships its native binary as a platform-specific optional dependency package (e.g. `@img/sharp-linux-x64`, `@img/sharp-win32-x64`), and npm only installs the variant matching whatever OS `npm install` actually ran on. Since this container is Linux, `node_modules/@img` only ever had the Linux (and linuxmusl/wasm32 fallback) binaries — `electron-builder` faithfully packaged those into the Windows build, and Windows obviously can't load Linux native code. Fixed by prepending `npm install --no-save --os=win32 --cpu=x64 sharp` to both `dist` and `dist:local` — npm's `--os`/`--cpu` flags force-fetch the win32-x64 optional package alongside (not instead of) the Linux ones already present, since they're separate package names and coexist fine in `node_modules`; `sharp`'s own JS entry point picks the right one at runtime via `process.platform`. `--no-save` keeps it out of `package.json`/`package-lock.json` since it's a build-time-only concern for this container, not a real project dependency. On the GitHub Actions Windows runner this line is a harmless no-op (the correct binary is already the native one `npm ci` installed there); it only matters when cross-packaging for Windows from a non-Windows host. Verified for real: rebuilt, confirmed `@img/sharp-win32-x64/lib/sharp-win32-x64-*.node` present in both `release/win-unpacked/` and the copied `PurgeWave-win/`.

## Non-negotiables

- There is no skip / "decide later" gesture — every card resolves to keep or discard (spec §6.4, §9.4).
- Undo must restore exact prior state (the `n` review count must not be left incremented, pass-2 `r` timestamp restored) and is unavailable once files are actually disposed of — Windows owns that restore.
- The quarantine/move destination is always excluded from scans, even if nested inside the library root.
- Duplicate detection, tag editing, playlists, multiple library roots, and preview scrubbing are explicitly out of scope for v1 — don't build toward them.
